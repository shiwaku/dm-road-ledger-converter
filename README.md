# dm-road-ledger-converter

## 概要

道路台帳図のDM（数値地形図データファイル）をGeoJSON形式に変換します。線・面・記号・方向・注記の5種類に分割して出力します。

出力したGeoJSONは、QGIS等での地図表示のほか、GeoParquetへの変換や、tippecanoe・pmtiles によるベクトルタイル化を経てWeb地図での利用ができます。

[dm-converter](https://github.com/shiwaku/dm-converter) の派生です。道路台帳図は座標値の単位や含まれる地物が異なるため、リポジトリを分けています。差異は[dm-converter との違い](#dm-converter-との違い)を参照してください。

## 道路台帳図とは

道路台帳図は、**道路法第28条・道路法施行規則第4条の2**に基づき、道路管理者（国・都道府県・市区町村）が路線ごとに調製・保管する法定台帳の**図面（附図）**部分です。

道路台帳は図面（附図）と調書の2部で構成され、本ツールが扱うのは図面のほうです。図面には道路区域境界・幅員・縦断勾配・曲線半径・舗装種別・トンネル/橋梁名・道路附属物・敷地の国有/民有別等の記載が義務づけられており、道路の新設・改築・廃止のたびに更新されます。

道路管理者ごとに整備されるため、同一地域でも管理者が異なれば別のデータになります。

### 縮尺

法定の最低基準は縮尺1/1,000以上です。実際の整備縮尺は地域によって分かれます。

| 縮尺 | 主な整備対象 |
|---|---|
| 1/500 | 市街地・住宅密集地 |
| 1/1,000 | 郊外・農村部・山間部 |

DMのMレコードには地図情報レベル（`500`・`1000`）として記録されており、本ツールが自動で読み取ります。

なお路線網図・路線番号図は道路法施行規則が義務づける附図には含まれず、法定の道路台帳附図ではありません。

> 出典: 道路法（昭和27年法律第180号）第28条、道路法施行規則（昭和27年建設省令第25号）第4条の2

## 対応範囲

| レコード | 内容 | 出力 |
|---|---|---|
| `E1` | 面 | `道路台帳図_面.geojson` |
| `E2` | 線 | `道路台帳図_線.geojson` |
| `E5` | 点（記号） | `道路台帳図_記号.geojson` |
| `E6` | 方向 | `道路台帳図_方向.geojson` |
| `E7` | 注記 | `道路台帳図_注記.geojson` |
| `E3` | 円 | 変換対象外（件数を警告） |
| `E4` | 円弧 | 変換対象外（件数を警告） |
| `E8` | 属性 | 変換対象外（件数を警告） |
| `G`・`T` | グリッド・TIN | 読み飛ばし |

`E2`（線）のうち始終点が一致するものは面として扱い、`E1` に振り分けます。

### 変換対象外のレコード

円（`E3`）・円弧（`E4`）・属性（`E8`）は出力しません。含まれていた場合は
**変換の最後に件数と該当ファイルを警告として出します。**

```
警告: 変換対象外のレコードを 6 件読み飛ばしました（出力には現れません）
  E4 円弧: 3件
  E3 円: 2件
  E8 属性: 1件
  該当ファイル: 1件
    /path/to/06oc5708.dm
```

レコード送りはレコード数から求めているため、**読み飛ばしてもファイルの解析は壊れません**
（後続の線・記号・注記はそのまま変換されます）。ただし該当する地物は出力に現れないため、
図面と見比べたときの食い違いの原因になります。円弧を使うDMも属性レコードを持つDMも
正常なデータなので、**警告を出すだけで終了コードは変えません**。

道路台帳平面図は隅切り・街角の曲線が多く、作成元によっては円弧が使われている可能性が
あります。同梱の豊中市サンプルには `E3`・`E4`・`E8` が1件も入っていないため、
この警告はサンプルでは出ません。

### DMデータの構造

DMファイルは84バイト固定長のレコードが並んだテキストファイルです。

- **Mレコード**（図郭）— 図郭コード・地図情報レベル・図郭の左下座標を持ちます。座標は平面直角座標系のメートル値です
- **Eレコード**（要素）— ヘッダに分類コード・実データ区分・データ数・レコード数を持ち、直後に実データ行が続きます
- **実データ行** — 図郭左下からのオフセット座標。**単位はミリメートル**です

要素の座標は「図郭左下（メートル）＋ オフセット（ミリメートル）」で求めます。

## 前提条件

- Node.js 18 以上

依存パッケージは `iconv-lite`（文字コード変換）と `proj4`（座標変換）の2つだけです。

## 利用方法

```bash
# ../DMデータ/ を再帰検索して変換
node src/index.js

# 入力フォルダを指定
node src/index.js --input /path/to/dm_dir

# 座標系を指定（大阪府＝第6系）
node src/index.js --epsg 6674 --input /path/to/dm_dir

# 並列数を指定
node src/index.js --jobs 4 --input /path/to/dm_dir

# 逐次実行
node src/index.js --jobs 1 --input /path/to/dm_dir
```

入力フォルダは**サブフォルダを再帰的に検索**します。道路台帳DMは路線ごとにフォルダが分かれていることが多いためです。

### オプション

| オプション | 既定値 | 説明 |
|---|---|---|
| `--input` | `../DMデータ/` | 入力フォルダ（再帰検索） |
| `--epsg` | `6674` | 入力データの座標参照系。JGD2011 第6系（京都・大阪ほか） |
| `--jobs` | CPUコア数-1 | 並列数。`1` で逐次実行 |

縮尺は指定しません。Mレコードから自動で読み取り、フィーチャごとに `Scale` 属性として出力します。1回の実行に複数の縮尺が混在していても正しく記録されます。

### 豊中市サンプルでの実行例

豊中市が道路台帳平面図DM500のサンプル（図郭57-08・市役所付近）を[無償公開](https://www.city.toyonaka.osaka.jp/machi/doro/daityou/digitalmap/sanple.html)しています。DM・DXF・PDF・シェープファイルの4形式が入っており、動作確認に使えます。

```bash
node src/index.js --epsg 6674 --input /path/to/DM_57-08/dm
```

大阪府のため第6系（EPSG:6674）を指定します。

| 種別 | 件数 |
|---|---|
| 線 | 2,647 |
| 面 | 400 |
| 記号 | 1,210 |
| 方向 | 1,473 |
| 注記 | 95 |

### 並列実行

並列実行はファイルを連続したかたまりに分けて処理し、断片を元の順序で連結します。そのため**逐次実行とバイト単位で同じGeoJSON**になります。ラウンドロビンで分けると出力順が変わり結果を比較できなくなるため、この方式を採っています。

### 出力ファイル

| ファイル名 | 内容 |
|---|---|
| `道路台帳図_線.geojson` | 線要素（E2） |
| `道路台帳図_面.geojson` | 面要素（E1） |
| `道路台帳図_記号.geojson` | 記号・点要素（E5） |
| `道路台帳図_方向.geojson` | 方向要素（E6） |
| `道路台帳図_注記.geojson` | 注記要素（E7） |

### 出力GeoJSONの属性

全種別に共通する属性です。

| 属性名 | 説明 | 例 |
|---|---|---|
| `Code` | 分類コード | `2101` |
| `Elno` | 要素識別番号（図郭コード-分類コード-連番） | `06OC5708-8114-0001` |
| `Scale` | 地図情報レベル（Mレコードから自動取得） | `500`、`1000` |
| `Elev` | 標高値（メートル）。対象は等高線と標高点のみ（[標高値について](#標高値について)） | `27.3`、`27.0`、`25` |
| `RecordType` | レコードタイプ | `E1`、`E2`、`E5`、`E6`、`E7` |
| `DataType` | データタイプ（日本語） | `面`、`線`、`点`、`方向`、`注記` |
| `DataKind` | 実データ区分 | `0`、`1`、`2`、`3`、`4`、`6` |

注記（E7）に追加される属性です。

| 属性名 | 説明 | 例 |
|---|---|---|
| `Text` | 注記文字列 | `中桜塚二丁目` |
| `Vnflag` | 縦横フラグ | `0`（横書き）、`1`（縦書き） |
| `Angle` | 文字の角度（度） | `-90` |

方向（E6）に追加される属性です。

| 属性名 | 説明 | 例 |
|---|---|---|
| `Angle` | 向き（度） | `144` |
| `Seq` | 要素内の通し番号 | `1`、`2` |

`Elno` の先頭は図郭コードです。Mレコードの図郭コードが空欄のデータでは先頭がハイフンになります（空欄のデータは珍しくありません）。

#### 方向（E6）について

方向要素は起点と方向点の2点で1本を表します。第1点が地物の位置、第1点から第2点への向きが方向です。2点間の距離は図上の記号長に相当する定型値で実長ではないため、**線としては出力せず、起点の位置と角度に変換**しています。

1つのE6要素に複数のペアが入ることがあります。豊中サンプルでは要素の8.4%が該当し、最大20点＝10本でした。**ペアごとに1フィーチャ**として出力し、同一要素から出た複数件は `Seq`（1始まり）で区別します。`Elno` は要素の識別番号なので重複します。一意なキーが必要な場合は `Elno` と `Seq` を組み合わせてください。

角度はDMのX（北方向）・Y（東方向）から、**水平右（東）を0度とする反時計回りの度数**に変換しています。注記（E7）の `Angle` と同じ規約に揃えてあるため、描画側は同じ変換で扱えます。

#### 注記の文字コードについて

DMの注記の文字コードは**データ作成元によって異なります**。

| 方式 | 特徴 |
|---|---|
| Shift-JIS（cp932） | 8ビット目が立つ。余白は半角スペース（`0x20`） |
| JIS X 0208（7bit） | 全バイトが `0x21`〜`0x7E`。余白は全角スペース（`0x21 0x21`）の連続 |

7bitの範囲だけで構成される注記は、ASCII（幅員等の数値）とJISの区別がつきません。記号の有無などで推測すると `1?` が `運` になるような誤変換を招くため、**全角スペース埋めという明確な痕跡がある場合に限りJISとして扱います**。

JIS X 0208（7bit）は各バイトに `0x80` を足すとEUC-JPになるため、その変換を経てデコードしています。豊中サンプルの注記95件はすべてこの方式で、文字化けなくデコードできることを確認しています。

なお注記に含まれる `￥`（JIS `216F`）は**改行位置を表すマーカー**です。豊中サンプルでは95件中12件に含まれます（例: `光陵￥マンション` は2行で表示される建物名）。**出力時に改行（`\n`）へ置き換えます。** GeoJSONでは `"光陵\nマンション"` とエスケープされ、MapLibre の `text-field` はこれを改行として描くため、図面と同じ2行になります。

#### 実データ区分と座標の単位

実データ区分（`DataKind`）は1点あたりのバイト数を決めます。

| 区分 | 内容 | 1点のバイト数 | 1レコードの点数 |
|---|---|---|---|
| `0` | データなし（記号の代表点） | — | — |
| `1` | 一次元 | — | — |
| `2` | 二次元（X,Y） | 14 | 6 |
| `3` | 三次元（X,Y,Z） | 21 | 4 |
| `4` | 注記 | — | — |
| `6` | 三次元（X,Y,Z） | 21 | 4 |

**区分 `6` も三次元レイアウト**です。14バイトとして読むと座標が壊れます。区分 `6` を含む実データで、`ceil(データ数 ÷ 4) = レコード数` が全要素で成立することと、実データ行がX,Y,Zの3つ組で並んでいることを確認しています。Z値は使用していません。

なお豊中市サンプル（図郭57-08）の実データ区分は `0`（記号1,210件）・`2`（線・面4,520件）・`4`（注記95件）のみで、**区分 `3`・`6` は含まれません**。三次元の挙動はこのサンプルでは再現できません。

#### 標高値について

標高点や等高線の標高は、**注記（E7）ではなくEレコードの標高値フィールド（50〜56桁）**に入っています。単位はミリメートルで、`Elev` 属性としてメートルに直して出力します（`27300` → `27.3`）。

```
E67312 0   0  78 2 02440 00   2   1      0      0  27300 0       9710              1
                                                   ^^^^^ 標高値 27.300m
```

**このフィールドは分類コードによって意味が変わります。** そのため `src/convert.js` の `ELEV_CODES`（等高線 `7101`〜`7107`、標高点 `7311`・`7312`）に限って標高として出力し、それ以外では値を捨てています。分類コードを解釈しないという本ツールの方針の例外ですが、コードを見なければ標高か点番号かを判別できません。

| コード | フィールドの中身 | 根拠 |
|---|---|---|
| `7312` 図化機測定による標高点 | 標高（mm） | 262件すべてに値。提供元のシェープファイル版の標高値（`TEXTCODE1`）と多重集合で完全一致 |
| `7101`・`7102` 等高線 | 標高（mm） | 計152件すべてに値。`25000`・`26000` など計曲線・主曲線の間隔と整合 |
| `7311` 標石を有しない標高点 | **未記録（`0`）** | 70件すべて0。レコード全体を探しても標高値が無い（シェープファイル版は別途 `Z_COORD` に持つ） |
| `7304`・`7306` 基準点 | **点番号** | DM `3013400` に対しシェープファイル版は点番号 `30134`。標高は別フィールド |

`0` は未記録として出力しません。標高0.000mの地物も落ちますが、実在するとしても海面高の等高線だけです。注記（E7）は同じ位置の意味が確認できていないため対象外にしています（注記の数値は `Text` に入ります）。

**標高点は小数1桁に揃えます**（`27000` → `27.0`）。割り切れると `27` になり、隣に並ぶ `26.1` と桁数が揃わず標高だと読み取りにくくなるためです。桁を増やすだけで丸めはしません（`25730` は `25.73` のまま）。等高線は図面が整数で描くのでそのままです。

同梱のPDF図面（`DM-_57-08.pdf`）と突き合わせると、PDFは `7311` の位置に67個、基準点の位置に7個の標高を描いています。**これらはDMに入っていない値**です（PDFとシェープファイル版だけが持っている）。逆に `7312` は262件のうち照合できた259件が一致しました。

ビューワは `Elev` を数値ラベルとして描きます（標高点は記号の右脇（図面と同じ位置）、等高線は線に沿って）。

## dm-converter との違い

[dm-converter](https://github.com/shiwaku/dm-converter) は地図情報レベル2,500・10,000のDMを対象としています。**両者を入れ替えて使うことはできません。**

| | dm-converter | 本リポジトリ |
|---|---|---|
| 地図情報レベル | 2,500・10,000・25,000 | 500・1,000 |
| **座標オフセットの単位** | **センチメートル** | **ミリメートル** |
| 実データ区分3・6 | 未対応 | 対応 |
| 注記のJIS X 0208 | 未対応 | 対応 |
| 縮尺 | `--scale` で指定 | Mレコードから自動取得 |
| 入力フォルダ | 直下のみ | 再帰検索 |

座標オフセットの単位が違うため、**本ツールに1/2,500のデータを通すと図郭の隅1/10に潰れ、dm-converter に1/500のデータを通すと10倍に広がります**。

単位は図郭サイズと座標オフセットの実測から確認しています。

| データ | レベル | 図郭 | オフセット最大 | 単位 |
|---|---|---|---|---|
| 豊中市 道路台帳 | 500 | 300m × 400m | 400,000 | ミリメートル |
| 静岡市 レベル2,500 | 2,500 | 1,500m × 2,000m | 200,000 | センチメートル |
| 静岡市 レベル10,000 | 10,000 | 10,789m × 12,093m | 1,172,621 | センチメートル |

豊中の400,000はミリメートルなら図郭の400mと完全に一致します（センチメートルなら4,000mで図郭の10倍）。

## 座標系

DMファイルは平面直角座標系で記録されており、`--epsg` で系を指定します。出力するGeoJSONはEPSG:4326（WGS84の経緯度）に変換されます。

## 一括ビルド（GeoJSON + GeoParquet + PMTiles）

GeoJSONだけ作り直してGeoParquetやPMTilesが古いまま残ると、配信データと変換結果が食い違います。まとめて焼き直すスクリプトを用意しています。

```bash
# ../DMデータ/ を変換して一式を生成
scripts/build.sh

# 入力フォルダを指定
EPSG=6674 scripts/build.sh /path/to/DM_57-08/dm

# タイルだけ焼き直す
SKIP_CONVERT=1 SKIP_PARQUET=1 scripts/build.sh
```

### 環境変数

| 変数 | 効果 |
|---|---|
| `EPSG=6674` | 入力データの座標参照系を指定 |
| `JOBS=4` | 並列数を指定 |
| `MAXZOOM=17` | タイルの最大ズーム（既定18） |
| `MINZOOM=14` | タイルの最小ズーム（既定15） |
| `SKIP_CONVERT=1` | DM→GeoJSON を飛ばす |
| `SKIP_CHECK=1` | 拡張コードの点検を飛ばす（ネットワークが要るため） |
| `SKIP_PARQUET=1` | GeoParquet を作らない |
| `SKIP_TILES=1` | MBTiles / PMTiles を作らない |
| `VITE_DM_PROVIDERS=` | 点検で使う拡張DMの提供元（既定はビューワと同じ） |
| `ATTRIBUTION="..."` | タイルのメタデータに入れる帰属・承認の文言（tippecanoe `-A`）。測量成果の使用承認で明示を求められる文言を承認書の指定どおりに書く。未指定なら入れず、最後に注意を出す（[データ出典・利用上の注意](#データ出典利用上の注意)） |

### 必要なツール

いずれも無ければ該当する段だけスキップされ、変換自体は完了します。

| ツール | 用途 |
|---|---|
| [OSGeo4W](https://trac.osgeo.org/osgeo4w/) の ogr2ogr | GeoParquet 生成 |
| geopandas + pyarrow | GeoParquet 生成（ogr2ogr が使えない場合の代替） |
| [tippecanoe](https://github.com/felt/tippecanoe) | ベクトルタイル生成 |
| [go-pmtiles](https://github.com/protomaps/go-pmtiles) | PMTiles 変換 |

## 拡張コード（自治体独自コード）の点検

道路台帳図には公共測量標準図式に無い自治体・測量ベンダー固有のコードが混ざります。**豊中サンプル（図郭57-08）では105コード中28コード・860件（14.8%）がこれにあたります。** 混ざること自体は道路台帳図では普通のことで異常ではありませんが、どれが固有コードかを知らないまま扱うと静かに劣化するため、変換のたびに一覧します。

```bash
npm run check:extended         # 変換結果を点検する
npm run check:extended -- --json
```

`scripts/build.sh` は DM→GeoJSON の直後にこれを実行します（`SKIP_CHECK=1` で飛ばせます）。

```
■ 拡張コード（標準図式に無い）: 28 コード / 860 件（14.8%）
   コード  件数    地物          アイコン
   2229     133  線・面        （アイコンを使わない地物）
   4143     119  記号・方向    dm-4231（toyonaka の代替表）
   4145     100  記号・方向    dm-toyonaka-4145（toyonaka の区画）
   4191      82  記号          dm-4161（toyonaka の代替表）
   2245       5  方向          dm-ext1-2245（ext1 の区画）
   8132       3  記号・注記    ―（代替図形の丸）
```

判定の根拠は dm-sprite の [`data/standard-codes.csv`](https://github.com/shiwaku/dm-sprite/blob/main/data/standard-codes.csv)（453コード）です。標準か拡張かの機械判定のために起こされた表で、これだけが完全です。`viewer/src/dmCodes.ts`（435件）や dm-sprite の `data/symbols.csv`（372件）は欠けがあるため判定には使いません。ネットワークが使えない場合は隣に置いた `../dm-sprite` のクローンを見にいきます（`--codes=<path>` で差し替えもできます）。

終了コードは、**拡張DMのアイコンを持っているのに提供元を指定していない場合だけ** 1 になります。

```
!! 提供元の指定漏れ: 2 コード / 87 件
   2245（5件）→ ext1
   4191（82件）→ toyonaka
```

この状態はエラーにならないまま代替図形の丸に落ちるため、見た目からは気づけません（実際 `dm-2245` の改名で豊中サンプルの5件が黙って丸になっていたことがあります）。逆に、**別の自治体のデータで指定しないのは正しい判断**です。拡張DMコードの意匠は提供元ごとに違うため、当てるべきでない意匠を当ててしまいます。詳しくは[拡張DMコードの提供元を指定する](#拡張dmコードの提供元を指定する)を参照してください。

ビルドはこの検出では止まりません。タイル自体には影響せず、ビューワの表示だけの問題だからです。最後にもう一度警告を出します。

## ベクトルタイル

`scripts/build.sh` は以下のレイヤー構成でPMTilesを生成します。

| レイヤー名 | 元データ | 出現ズーム |
|---|---|---|
| `road_line` | 線（E2） | Z15〜 |
| `road_polygon` | 面（E1） | Z15〜 |
| `road_symbol` | 記号（E5） | Z17〜 |
| `road_direction` | 方向（E6） | Z17〜 |
| `road_annotation` | 注記（E7） | Z17〜 |

記号・方向・注記はZL17未満では小さすぎて読めないため、タイルに入れていません。

タイルに残す属性は `Code`・`Text`・`Angle`・`Elev` の4つだけです。`Elno` はフィーチャごとにユニークな文字列でタイル内の文字列辞書を最も膨らませるため落としています。`RecordType`・`DataType`・`DataKind`・`Scale`・`Vnflag`・`Seq` はレイヤー内でほぼ単一値か表示専用のため同様です。

### 最大ズームレベルの決め方

ベクトルタイルは座標をタイル内の整数格子（0〜4,095）に量子化して格納するため、変換時にわずかな位置誤差が生じます。元データの精度を損なわないよう、**格子間隔（分解能）が地図の許容誤差以下**になる最小のZLを最大ズームレベルに選びます。

- **許容誤差** = 縮尺分母 × 0.1mm（図上0.1mmに相当する地上距離）
- **分解能** = 赤道周長 40,075,016.686m ÷ (2^ZL × 4,096)

| 地図情報レベル | 許容誤差 | 最大ZL | そのZLの分解能 | 1段下のZLの分解能 |
|---|---|---|---|---|
| 500 | 0.05m | **18** | 0.037m | 0.075m ✗ |
| 1,000 | 0.1m | **17** | 0.075m | 0.149m ✗ |

分解能は赤道基準の最大値で、実際には緯度 φ において cos φ 倍に小さくなります。したがって日本国内では余裕をもって許容誤差を満たします。

1/1,000 のデータだけを扱う場合は `MAXZOOM=17` を指定するとタイル数を減らせます。

### 線・面の線幅と破線

**分類コードごとの線幅と破線は、同梱のPDF図面（`DM-_57-08.pdf`、A0のベクタPDF、1:500）の実測に合わせています。** 基本図ビューワが持っている公共測量標準図式の20パターンは使っていません。道路台帳図の分類コードは自治体・測量ベンダーによって運用が異なり、全国共通の図式として確定していないため、図式の書物ではなく図面そのものを基準にしています。

測り方は `scripts/measure-pdf.py` です。PDFの描画パスを平面直角座標に載せ（図枠のグリッドラベルから 5.6687 pt/m）、変換結果の線・面に投影して被覆区間を取り、線幅と実線／空白の長さを読みます。**図面は dash 属性を使わず短い実線の連なりで破線を描く**ので、パターンはこうして測るしかありません。

```bash
python3 scripts/measure-pdf.py lines
```

図面の線幅は 0.30 / 0.42 / 0.54 / 0.84 pt の4種類で、図式どおりに分かれていました。既定は最も多い 0.42pt です。

| 0.54pt | `7101` 等高線（計曲線）・`1106` 大字・町・丁目界 |
| 0.42pt（既定） | `2101` 道路縁・`3001` 普通建物 ほか |

### 分類コードの名称

ポップアップでは分類コードの直後に公共測量標準図式の名称を出します（`2235` → 雨水桝）。対応表 `viewer/src/dmCodes.ts` は [dm-converter の同名ファイル](https://github.com/shiwaku/dm-converter/blob/main/viewer/src/dmCodes.ts)の複製です。図式は共通なので、どちらかを直したらもう一方にも同じ修正を入れます。

豊中サンプル（図郭57-08）では105コード中77コード、フィーチャ数では5,825件中4,965件（85.2%）に名称が付きます。標準図式に無いコードは「（標準図式に記載なし）」と出します。名称が出ないこと自体が「自治体固有のコードだ」という情報になるため、コードは隠しません。

> 名称表に無いコード（28コード）と、標準図式そのものに無いコード（28コード）は**別の話**です。名称表は図式の写しなので豊中サンプルではたまたま一致しますが、根拠が違います。前者は `cd viewer && npm run check:codes`、後者は `npm run check:extended` で確かめます。

名称表とスプライトは別々に育つので、整合を確かめるスクリプトを用意しています。

```bash
cd viewer && npm run check:codes
```

アイコンがあるのに名称が無いコードを検出します（あると「アイコンは出るのに記載なしと表示される」中途半端な状態になります）。dm-sprite は随時更新されるため、アイコン数はドキュメントに書かずこれで数えます。

**落とすのは標準図式のコードだけです。** 拡張コードは図式に名称が無いため名称表に足しようがなく、アイコンが増えるたびに落ちて直しようのない指示を出すことになります（豊中市の区画が dm-sprite に入った時点で実際に8コードが該当しました）。標準か拡張かの判定は `scripts/standard-codes.mjs` を通し、拡張コードは「名称表の対象外」として別に並べます。

### 記号・方向のアイコンと代替図形

記号・方向のアイコンは公共測量標準図式のコードと共通なので、[dm-sprite](https://github.com/shiwaku/dm-sprite) をそのまま使います（アイコン数は随時増えるため `npm run check:codes` で数えます）。ただし道路台帳図には図式に無い自治体固有のコードが混ざるため、**スプライトのアイコンが無いコードは丸で位置を示します**。

起動時にスプライトの索引（`sprite.json`）を読み、アイコンのあるコードとないコードを排他フィルタの2レイヤーに振り分けています。アイコンの無いコードをそのまま `icon-image` で要求すると、その地物は何も描かれず黙って消えるためです。索引が読めなかった場合は全コードを代替図形で描きます。

#### 拡張DMコードの提供元を指定する

dm-sprite はアイコンを2種類に分けて配っています（[dm-sprite#23](https://github.com/shiwaku/dm-sprite/issues/23)）。

```
dm-4132            標準図式。全国共通なので区画なし
dm-ext1-2245       拡張DM。提供元が未特定のもの
dm-ext1-9101100    同（分類コードが7桁のもの）
dm-toyonaka-4145   拡張DM。豊中市の運用（豊中市の区画）
```

**いま dm-sprite にある区画は `ext1`（6コード）と `toyonaka`（7コード。2026年8月15日の [dm-sprite#30](https://github.com/shiwaku/dm-sprite/pull/30) から）です。** 豊中市の区画には `4191` が入っていません（図面では標準の `4161` と同じ意匠なので、dm-sprite は「図面に無い区別は発明しない」方針で作らないと決めた）。そのため `4191` は後述の代替表で `dm-4161` を指して解決しています。設定の `toyonaka` は、**区画と代替表の両方を引き当てるキー**として働きます。

もし将来 `dm-toyonaka-4191` が配信されれば、ビューワは**無修正でそちらへ切り替わります**（区画のアイコンは代替表より先に採るため）。切り替わったら代替表の `4191` の行は不要になるので外してください。`npm run check:extended` の出力が `dm-4161（toyonaka の代替表）` から `dm-toyonaka-4191（toyonaka の区画）` に変わるのが目印です。

拡張DMコードの意匠は提供元ごとに違うため、**表示するデータの提供元と一致していなければ他所の意匠を当ててしまいます。** どの提供元のPMTilesかはビューワからは判定できないので、既定は同梱の検証データ（豊中市サンプル）に合わせた `ext1,toyonaka` にしてあります。

```bash
# 別の自治体のDMを焼いて表示するとき（必ず上書きするか空にする）
VITE_DM_PROVIDERS= npm run dev
VITE_DM_PROVIDERS=yourcity npm run dev
```

カンマ区切りで、書いた順に優先します。同じコードに標準と拡張の両方がある場合は標準を優先します。挙げなかった提供元の拡張DMコードはアイコンを引けず代替図形の丸で描かれます。位置は出るので地物が消えることはありません。

#### 既存アイコンで代替する

dm-sprite は「どんなアイコンが存在するか」だけを持ち、**どのコードをどのアイコンで代替するかは、そのデータを扱う側の判断**という切り分けになっています（[dm-sprite#22](https://github.com/shiwaku/dm-sprite/issues/22)）。図面から起こした意匠が既存アイコンと同じなら、同じ絵を別のキーで二重に配らず、利用側が既存のキーを指します。

その対応表が `src/basemap.ts` の `ICON_ALIASES` です。**提供元ごとに持ちます。**

| 分類コード | 代替先 | 根拠 |
|---|---|---|

### アイコンの大きさ

**アイコンには全コード一律で 0.5 倍を掛けています。** dm-sprite のアイコンは 64x64 のキャンバスですが実際に描かれている範囲は 6〜44px とばらつき、倍率1.0のままだと図面より大きく描かれていました。

```bash
python3 scripts/measure-pdf.py symbols
```

PDF図面の記号49コードを実測し、スプライトのインク寸法（アルファ>8 の外接矩形）と比べると、倍率1.0では図面の **1.8倍**（コード単位の中央値）／**2.2倍**（件数で重み付けした中央値）ありました。

| 分類コード | 件数 | 図面での大きさ | 倍率1.0での大きさ |
|---|---|---|---|
| `6331` 広葉樹林 | 358 | 0.91m | 1.35m |
| `3401` 門 | 306 | 0.65m | 0.98m |
| `4151` マンホール | 175 | 1.06m | 2.45m |
| `6214` | 101 | 1.08m | 2.94m |

分類コードごとの補正はしていません。ラスタのスプライトを引き伸ばすと輪郭がぼやけるためです。コードごとの比率は 0.7〜6.1倍とばらついたままで、これは dm-sprite のインクの大きさが揃っていないことに由来します（[dm-sprite#15](https://github.com/shiwaku/dm-sprite/issues/15)）。**dm-sprite が更新されたら測り直してください。**

ダークテーマでもスプライトのアイコンの色はそのままです（アイコンはSDFではない画像のため MapLibre 側で色を変えられません）。基本図ビューワと同じ挙動です。

### 注記・方向の角度

DMの角度は「水平右（東）を0度とする反時計回り」です。MapLibre の `text-rotate` / `icon-rotate` は時計回りが正で、回転前の文字列・アイコンはどちらも右（東）向きなので、**符号を反転するだけ**で読み替えられます。

注記だけは、基本図ビューワと同じく角度が ±90 のときに 0 へ倒します。豊中市サンプルでは ±90 度の注記29件すべてが縦横フラグ=1（縦書き）で、角度 ±90 は「文字列を寝かせる」指示ではなく縦書きの表現でした。そのまま回すと、縦書きのはずの注記が横倒しの文字列として出ます。

本来の縦書き（文字を縦に積む）を出すには MapLibre の `text-writing-mode` が必要ですが、データ駆動にできず、そもそも縦横フラグがタイルに載っていない（`TILE_ATTRS` は `Code` / `Text` / `Angle` のみ）ため、横書きとして描いています。

注記・標高値の文字は地理院の最適化ベクトルタイルのグリフを借りて描いています。同グリフに含まれるフォントは `NotoSansJP-Regular` だけなので、`text-font` はこれを明示する必要があります。明示しないと MapLibre 既定の `Open Sans Regular` を要求して404になり、文字が黙って消えます。

### 帰属・承認番号の表示

測量成果の使用承認には「成果品の見やすいところに承認番号を明示すること」が条件として付きます。ビューワは右下の帰属コントロール（ⓘ）とパネル下部の脚注の2か所に、`VITE_DM_ATTRIBUTION` の文言をそのまま出します。**文言は承認書の指定どおりに書き、言い換えません。**

どのPMTilesを表示しているかはビューワからは判定できないため、`VITE_DM_PROVIDERS` と同じく**既定は同梱の検証データ（豊中市サンプル）の承認番号**です。別のデータを焼いて表示するときは必ず上書きするか空にしてください。空にすると帰属コントロールと脚注からこの文言が消えます（他所の承認番号を出さないため）。

```bash
VITE_DM_ATTRIBUTION= npm run dev                                   # 文言を出さない
VITE_DM_ATTRIBUTION='測量法に基づく○○市長承認（使用）第○号' npm run dev   # 別の承認番号
```

タイル単体で QGIS 等に読まれる場合に備えて、`scripts/build.sh` の `ATTRIBUTION` で PMTiles のメタデータ（`attribution`）にも同じ文言を入れます。

## 検証

豊中市が公開している同一図郭のシェープファイル版と突き合わせ、変換結果に欠落がないことを確認しています。

- DMファイルのEレコード数（5,627）と、変換したフィーチャ数（E6の複数ペア展開前）が完全に一致
- 分類コード単位で105コード中95コードが完全一致
- 残る差はシェープファイル側の派生生成によるもの（線から記号を生成している、要素をさらに分割している）で、DMの生レコードとは本ツールの出力が一致

### PDF図面との全数照合

`scripts/measure-pdf.py` が「描き方」を測るのに対し、`scripts/reconcile-pdf.py` は**地物の有無**を両方向で照合します。

```bash
python3 scripts/reconcile-pdf.py
python3 scripts/reconcile-pdf.py --crops   # 説明できないインクを切り出す
```

図郭（400×300m）で切り、PDFの描画パスを1本ずつ変換結果に当てて説明できるかを見ます。豊中サンプルでの結果です。

| 方向 | 結果 |
|---|---|
| 図面 → 変換結果 | 描画パス16,737本のうち16,659本を説明。残り78本 |
| 変換結果 → 図面 | 線・面3,047本中2本（`6136` 生垣）、記号・方向2,683件中1件（`8132`）にインクなし |
| 注記 | 図郭内94件すべてに対応する文字が図面にある |

**説明できない78本の内訳は、紙に出ないヘアライン45本（0.06pt以下。1:500では0.01mm）・図郭の枠線1本・実際に描かれている線32本（1.02pt・227.7m）です。** 延長で語ると図郭を貫くヘアラインだけで2割近くを占めるため、線幅で分けて数えます。

残る32本は国道176号の東側に沿って走り、街区の中へ枝分かれする太い線で、DMに対応する要素がありません（最寄りの変換線から0.6〜7.5m離れている）。道路区域線に見えますが、DMに無い以上ビューワには出せません。

図面にしか無い文字は363スパンで、うち338が数値、336は記号・方向の位置にある**標高値**です。DMに値が入っているのは `7312`（262件）だけで、`7311`（70件すべて0）と基準点の分は出ません。

### PDF図面とのラスタ差分（描いた結果）

有無の照合も実測も「変換結果とスタイルの指定値」しか見ていません。衝突判定で間引かれるラベル、縦書き、線幅が**実際にどう出ているか**は、描いたものを測らないと分かりません。`scripts/raster-diff.py` はビューワを図郭と同じ範囲・縮尺・方位でヘッドレス描画し（`viewer/scripts/render-sheet.mjs`）、PDFの同じ範囲と重ねて「そのマスにインクがあるか」を数えます。画素の一致は狙いません（アンチエイリアス・ハローで必ず外れる）。

```bash
python3 scripts/raster-diff.py                       # 4px/m（zoom 17.97）で全体を比べる
python3 scripts/raster-diff.py --breakdown           # インクを線・記号・文字に分ける（描画4回）
python3 scripts/raster-diff.py --breakdown --reuse   # 前回のPNGを使い、PDF側だけ計算し直す
python3 scripts/raster-diff.py --breakdown --ppm 8.157   # z19（1m＝8.157px）で
```

Chrome と pymupdf・pyproj・numpy・Pillow・shapely が要ります。**最初に出る「位置合わせの検算」が (0, 0) 付近であることを必ず確かめてください。** 範囲・縮尺・方位のどこかを間違えると、絵はそれらしいまま数字だけが静かに悪化します。重ね絵は `output/render/overlay*.png`（赤＝ビューワだけ／青＝図面だけ／黒＝両方）に出ます。

豊中サンプルの結果です。5m角のマスで見た一致率は94.9%（4,800マス中 両方4,071／ビューワだけ126／図面だけ91）ですが、**インクの総量はビューワが図面の1.58倍**ありました。`--breakdown` でこれを分けたのが次の表です。

| 内訳（px） | 4px/m（zoom 17.97） | | | z19（8.157px/m） | | |
|---|---:|---:|---:|---:|---:|---:|
| | ビューワ | 図面 | 比 | ビューワ | 図面 | 比 |
| 線・面 | 218,909 | 153,825 | 1.42 | 461,774 | 474,640 | 0.97 |
| 記号・方向 | 51,269 | 12,293 | 4.17 | 53,221 | 41,365 | 1.29 |
| 文字 | 39,354 | 13,417 | 2.93 | 45,367 | 43,668 | 1.04 |
| 図郭の枠線（図面のみ） | ― | 5,596 | | ― | 20,381 | |
| **合計** | **294,811** | **186,565** | **1.58** | **552,428** | **580,171** | **0.95** |

**1.58倍はほぼ「測った縮尺」の問題でした。** ビューワは記号・文字・線幅を地上サイズ固定で描き、z19 未満では z19 の値で頭打ちにしています（[アイコンの大きさ](#アイコンの大きさ)）。4px/m は zoom 17.97 なので、記号と文字が z19 の約2倍の地上サイズで出ていたのです。1:500 の図面と同じ地上サイズになる z19 で測り直すと、合計は 0.95倍、線・面 0.97倍、文字 1.04倍に収まります。z19 で残る差は次の2つです。

- **記号・方向が 1.29倍。** 大きさは `ICON_SCALE = 0.5` で図面に合わせてある（実測の中央値 1.0）ので、残りはアイコンの線の太さです。図面の記号は 0.3〜0.42pt（0.05〜0.07m）の細線で、スプライトの線はそれより太い
- **等高線のラベルの数。** 画面に出た数はビューワ73（z19）／23（zoom 17.97）に対し図面19で、ズームで変わります（[Issue #9](https://github.com/shiwaku/dm-road-ledger-converter/issues/9)）。標高点は 262／336 で、差の74件はDMに標高が無い `7311` と基準点のぶんです。注記は図面251スパン対ビューワ94件ですが、図面は2行の名称や縦書きを複数のスパンに分けるので、数はそのまま比べられません

線幅（インク÷延長）は z19 でビューワ 0.143m／図面 0.154m とほぼ同じです。4px/m ではビューワ 0.282m／図面 0.214m で、これも頭打ちの効果です。

**PDF側の分け方**は、`page.get_drawings()` の描画パスを線幅・塗り・記号（記号の位置の周りにある小さなパス。線に沿うものは除く）に分け、`Shape` で新しいページに描き直してラスタにしています。全部を1枚に描き直すと元の絵と 182px を除いて完全に一致します。種類ごとに別々に描くと、2本の細い線が隣り合う画素が片方ずつでは閾値を越えず、1〜2%（4px/m で 2,284px）だけ元の絵より減ります。図面は**白い塗りで下の線を消してから記号を描く**箇所があるため、白いパスは「マスク」として元の順番で全部の種類に割り込ませます（これをしないと、消されるはずの線が線の絵に残り、白の上の記号が消えます）。文字は、文字だけを消したPDF（redaction）との差で取ります。
