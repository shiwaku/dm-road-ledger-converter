# 検証

変換結果は同梱の豊中市サンプル（図郭57-08）だけで検証しています。誰でも同じ手順で入手でき、結果を公開できるデータに限るためです（[検証データ調査](検証データ調査.md)）。同じ図郭のシェープファイル版・PDF図面が同梱されているため、3方向から突き合わせられます。

| 見るもの | スクリプト | 何が分かるか |
|---|---|---|
| シェープファイル版 | （手作業） | 変換結果に欠落がないか |
| 図面にある地物の有無 | `scripts/reconcile-pdf.py` | 図面にあってDMに無いもの・その逆 |
| 図面の描き方 | `scripts/measure-pdf.py` | 線幅・破線・記号の大きさ・字高の実測値 |
| 描いた結果 | `scripts/raster-diff.py` | ビューワの描画とPDFのインクの差 |

## シェープファイル版との突き合わせ

豊中市が公開している同一図郭のシェープファイル版（`data/.../SHP_5708/shp`）と分類コード単位で比較しています。

- DMファイルのEレコード数（5,627）と、変換したフィーチャ数（E6の複数ペア展開前）が完全に一致
- 分類コード単位で105コード中95コードが完全一致
- 残る差はシェープファイル側の派生生成によるもの（線から記号を生成している、要素をさらに分割している）で、DMの生レコードとは本ツールの出力が一致

変換自体の回帰は、逐次実行と並列実行の出力がバイト単位で一致することでも確認できます（[並列実行と出力順](output-spec.md#並列実行と出力順)）。

## PDF図面との全数照合

`scripts/measure-pdf.py` が「描き方」を測るのに対し、`scripts/reconcile-pdf.py` は**地物の有無**を両方向で照合します。

```bash
python3 scripts/reconcile-pdf.py
python3 scripts/reconcile-pdf.py --crops   # 説明できないインクを切り出す
```

図郭（400×300m）で切り、PDFの描画パスを1本ずつ変換結果に当てて説明できるかを見ます。豊中サンプルでの結果です。

| 方向 | 結果 |
|---|---|
| 図面 → 変換結果 | 描画パス16,737本のうち16,659本を説明。残り78本 |
| 変換結果 → 図面 | 線・面3,047本中2本（`6136` 生垣）、記号・方向2,683件中1件（`8132`）にインクなし |
| 注記 | 図郭内94件すべてに対応する文字が図面にある |

**説明できない78本の内訳は、紙に出ないヘアライン45本（0.06pt以下。1:500では0.01mm）・図郭の枠線1本・実際に描かれている線32本（1.02pt・227.7m）です。** 延長で語ると図郭を貫くヘアラインだけで2割近くを占めるため、線幅で分けて数えます。

残る32本は国道176号の東側に沿って走り、街区の中へ枝分かれする太い線で、DMに対応する要素がありません（最寄りの変換線から0.6〜7.5m離れている）。道路区域線に見えますが、DMに無い以上ビューワには出せません。

図面にしか無い文字は363スパンで、うち338が数値、336は記号・方向の位置にある**標高値**です。DMに値が入っているのは `7312`（262件）だけで、`7311`（70件すべて0）と基準点の分は出ません（[標高値について](output-spec.md#標高値について)）。

同じスクリプトが、ビューワが `Elev` から描く派生ラベルも数えます。等高線の標高と標高点の標高は注記（E7）ではないため、注記の照合には現れないからです。**変換結果が正しくても候補が図面より多ければ描きすぎの元になります**（等高線はラベル候補152件に対し図面17か所で8.9倍）。ただしこれは「画面に何個出るか」ではありません。等高線のラベルは `text-allow-overlap: false` で衝突判定に任せてあり、実数はズームで変わります。画面上の数は[ラスタ差分](#pdf図面とのラスタ差分描いた結果)で測ります。

## 図面の描き方を実測する

`data/.../PDF_57-08/DM-_57-08.pdf` はA0のベクタPDFで、テキストもパスも座標つきで取り出せます。図枠のグリッドラベル（`-48,800`〜`-48,400`／`-135,000`〜`-135,300`）から PDF pt → 平面直角座標のアフィン変換が作れます（実測 5.6687 pt/m ＝ 1:500）。

```bash
python3 scripts/measure-pdf.py lines     # 線幅と破線パターン
python3 scripts/measure-pdf.py symbols   # 記号の大きさ
```

PDFの描画パスを平面直角座標に載せ、変換結果の線・面に投影して被覆区間を取り、線幅と実線／空白の長さを読みます。**図面は dash 属性を使わず短い実線の連なりで破線を描く**ので、パターンはこうして測るしかありません。

測った値をビューワのスタイルにどう反映しているかは[ビューワの「線・面の線幅と破線」](../viewer/README.md#線面の線幅と破線)・[「アイコンの大きさ」](../viewer/README.md#アイコンの大きさ)を参照してください。

## PDF図面とのラスタ差分（描いた結果）

有無の照合も実測も「変換結果とスタイルの指定値」しか見ていません。衝突判定で間引かれるラベル、縦書き、線幅が**実際にどう出ているか**は、描いたものを測らないと分かりません。`scripts/raster-diff.py` はビューワを図郭と同じ範囲・縮尺・方位でヘッドレス描画し（`viewer/scripts/render-sheet.mjs`）、PDFの同じ範囲と重ねて「そのマスにインクがあるか」を数えます。画素の一致は狙いません（アンチエイリアス・ハローで必ず外れる）。

```bash
python3 scripts/raster-diff.py                       # 4px/m（zoom 17.97）で全体を比べる
python3 scripts/raster-diff.py --breakdown           # インクを線・記号・文字に分ける（描画4回）
python3 scripts/raster-diff.py --breakdown --reuse   # 前回のPNGを使い、PDF側だけ計算し直す
python3 scripts/raster-diff.py --breakdown --ppm 8.157   # z19（1m＝8.157px）で
```

Chrome と pymupdf・pyproj・numpy・Pillow・shapely が要ります。**最初に出る「位置合わせの検算」が (0, 0) 付近であることを必ず確かめてください。** 範囲・縮尺・方位のどこかを間違えると、絵はそれらしいまま数字だけが静かに悪化します。重ね絵は `output/render/overlay*.png`（赤＝ビューワだけ／青＝図面だけ／黒＝両方）に出ます。

豊中サンプルの結果です。5m角のマスで見た一致率は95.1%（4,800マス中 両方4,077／ビューワだけ127／図面だけ85）ですが、**インクの総量はビューワが図面の1.59倍**ありました。`--breakdown` でこれを分けたのが次の表です。

| 内訳（px） | 4px/m（zoom 17.97） | | | z19（8.157px/m） | | |
|---|---:|---:|---:|---:|---:|---:|
| | ビューワ | 図面 | 比 | ビューワ | 図面 | 比 |
| 線・面 | 218,909 | 153,825 | 1.42 | 461,769 | 474,640 | 0.97 |
| 記号・方向 | 51,612 | 12,293 | 4.20 | 53,493 | 41,365 | 1.29 |
| 文字 | 39,858 | 13,417 | 2.97 | 45,414 | 43,668 | 1.04 |
| 図郭の枠線（図面のみ） | ― | 5,596 | | ― | 20,381 | |
| **合計** | **296,442** | **186,565** | **1.59** | **553,087** | **580,171** | **0.95** |

**1.59倍はほぼ「測った縮尺」の問題でした。** ビューワは記号・文字・線幅を地上サイズ固定で描き、z19 未満では z19 の値で頭打ちにしています（[アイコンの大きさ](../viewer/README.md#アイコンの大きさ)）。4px/m は zoom 17.97 なので、記号と文字が z19 の約2倍の地上サイズで出ていたのです。1:500 の図面と同じ地上サイズになる z19 で測り直すと、合計は 0.95倍、線・面 0.97倍、文字 1.04倍に収まります。**4px/m の内訳を「描きすぎ」と読んではいけません。** この縮尺は位置の一致（マス）を見る用途に留めます。

z19 で残る差は次の2つです。

- **記号・方向が 1.29倍。** 大きさは `ICON_SCALE = 0.5` で図面に合わせてある（実測の中央値 1.0）ので、残りはアイコンの線の太さです。図面の記号は 0.3〜0.42pt（0.05〜0.07m）の細線で、スプライトの線はそれより太い
- **等高線のラベルの数。** 画面に出た数はビューワ73（z19）／23（zoom 17.97）に対し図面19で、ズームで変わります（[Issue #9](https://github.com/shiwaku/dm-road-ledger-converter/issues/9)）。標高点は 262／336 で、差の74件はDMに標高が無い `7311` と基準点のぶんです。注記は図面251スパン対ビューワ94件ですが、図面は2行の名称や縦書きを複数のスパンに分けるので、数はそのまま比べられません

線幅（インク÷延長）は z19 でビューワ 0.143m／図面 0.154m とほぼ同じです。4px/m ではビューワ 0.282m／図面 0.214m で、これも頭打ちの効果です。

**PDF側の分け方**は、`page.get_drawings()` の描画パスを線幅・塗り・記号（記号の位置の周りにある小さなパス。線に沿うものは除く）に分け、`Shape` で新しいページに描き直してラスタにしています。全部を1枚に描き直すと元の絵と 182px を除いて完全に一致します。種類ごとに別々に描くと、2本の細い線が隣り合う画素が片方ずつでは閾値を越えず、1〜2%（4px/m で 2,284px）だけ元の絵より減ります。図面は**白い塗りで下の線を消してから記号を描く**箇所があるため、白いパスは「マスク」として元の順番で全部の種類に割り込ませます（これをしないと、消されるはずの線が線の絵に残り、白の上の記号が消えます）。文字は、文字だけを消したPDF（redaction）との差で取ります。
